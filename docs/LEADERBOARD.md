# Classic leaderboard contract

Positions rank completed, server-verified matches within the selected session duration and enemy spawn interval. A player may have multiple ranked matches. Ordering is score descending, elapsed whole seconds ascending, server recording time ascending, then match ID ascending using PostgreSQL C collation. Submission responses use the same configuration and all four tie-breakers. Other configurations do not affect the displayed position. The browser highlights its own rows by player ID.

Ranked Classic battles begin at `POST /api/session`. The response supplies the match ID, seed, configuration and anonymous player ID. A random HttpOnly, SameSite cookie authenticates the browser; its token is stored only as a SHA-256 hash. `POST /api/match` requires that session and an unexpired ticket, enforces request/timeline size bounds, rejects faster-than-real-time completion, replays the canonical rules, and compares the natural result. It never accepts the client's score or timestamp as proof. Only verified records enter `/api/ranking`. The match primary key ensures concurrent retries produce one result. Changed payloads on an already-recorded ID return 409.

Pagination executes a SQL count and a bounded SQL page, with a maximum page size of 50. Invalid numeric parameters and unsupported configuration values return 400. Error responses omit database internals. Leaderboard responses are not cached across result submission. Current-player highlighting is computed locally, keeping public board responses independent of browser identity.

Local MSW scenarios deliberately support synthetic results for gameplay and network fault injection. They share sorting, scope and query validation with the server, but are not evidence of server score verification. Security and SQL regression tests execute the actual handlers against an isolated PostgreSQL engine.

Run `npm.cmd test` for SQL/security/unit regressions and `npm.cmd run test:leaderboard` for desktop/mobile browser checks. The latter builds the live frontend, routes its API requests through the actual handlers with an isolated database, verifies natural gameplay submission and player highlighting, and proves forged results are rejected without entering the retry queue. Its test-only ticket clock permits fixed-tick fast-forwarding. Neither suite writes to Neon. CI runs these browser checks before deployment.

Deployment requires the `0001_vengeful_reavers` migration before the new Functions/frontend. Legacy records are retained in history and excluded from ranking. Deployments, provider state, edge CPU capacity, and bot prevention are separate from local correctness. Anonymous sessions and reproducible gameplay do not provide account ownership or detect bots.
